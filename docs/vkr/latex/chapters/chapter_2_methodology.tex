\subsection{Архитектура системы}
Система проектируется как клиент-серверное приложение. Клиентская часть реализует пользовательские экраны, локальное хранение и координацию сценариев. Серверная часть централизует бизнес-правила, доступ к данным и интеграцию с внешними сервисами. Такой подход поддерживает единый источник актуального состояния поездки при сохранении отзывчивости интерфейса \sref{12}\sref{13}\sref{14}.

Архитектурная схема фиксирует два уровня согласования данных: оперативный (онлайн-взаимодействие через API и каналы обновлений) и отложенный (офлайн-изменения с последующей синхронизацией). Такое разделение необходимо для мобильного сценария, в котором состояние сети не гарантировано \sref{19}.

\subsubsection{Архитектура клиентской части}
Клиент построен по многоуровневой схеме \texttt{UI -> ViewModel -> Repository -> Data source}.
\begin{enumerate}
    \item Слой интерфейса включает экраны Jetpack Compose и навигацию между пользовательскими сценариями.
    \item В слое представления используются \texttt{ViewModel} и потоки состояния (\texttt{StateFlow}/\texttt{SharedFlow}), что задает цикл «событие -> изменение состояния -> обновление экрана».
    \item Репозитории инкапсулируют работу с REST API, локальным кэшем и очередью синхронизации, чтобы экран не зависел от источника данных напрямую.
    \item Инфраструктурный слой включает внедрение зависимостей (Hilt) и фоновые задачи синхронизации (WorkManager), которые восстанавливают согласованность после появления сети.
\end{enumerate}

Такое разделение снижает связанность экранов с сетевыми деталями и позволяет развивать клиентские сценарии по модулям (поездки, идеи, маршрут, расходы) без дублирования сетевой и кэш-логики \sref{14}\sref{15}\sref{16}\sref{19}.

\subsubsection{Архитектура серверной части}
Сервер реализован как модульный backend на Ktor с явным разделением ответственности:
\begin{enumerate}
    \item Точка входа приложения инициализирует конфигурацию, подключение к базе данных, аутентификацию и общие плагины (логирование, сериализация, обработка ошибок, WebSocket).
    \item HTTP-маршруты сгруппированы по предметным областям (\texttt{auth}, \texttt{trip}, \texttt{idea}, \texttt{itinerary}, \texttt{expense}, \texttt{invite}, \texttt{notification}, \texttt{sync}), что упрощает сопровождение API.
    \item Предметные проверки и доступ к данным сосредоточены в серверных модулях и репозиториях, чтобы правила валидации и доступа не дублировались по маршрутам.
    \item Интеграции с внешними сервисами (погода, AI, уведомления) вынесены в отдельные компоненты, изолированные от ядра предметной логики.
\end{enumerate}

Для обсуждений используется отдельный WebSocket-канал: публикация нового комментария выполняется через событие в канале, при этом проверка прав участия в поездке остается на сервере \sref{12}\sref{13}\sref{17}\sref{18}.

\subsubsection{Взаимодействие клиента и сервера}
Взаимодействие строится в двух режимах:
\begin{enumerate}
    \item синхронный режим: REST API для операций по поездкам, идеям, маршруту, расходам и настройкам;
    \item событийный режим: WebSocket для новых комментариев и уведомления для фоновых оповещений.
\end{enumerate}

Сервер выступает источником истинного состояния, а клиент поддерживает локальную копию данных и очередь изменений. При нестабильной сети пользователь продолжает работу с локальными данными, после восстановления связи накопленные операции отправляются на сервер и состояние приводится к согласованному виду \sref{12}\sref{13}\sref{19}.

\subsection{Модель данных и связи сущностей}
Концептуальная модель данных строится вокруг сущности поездки как корневого объекта. Все функциональные подсистемы связаны с поездкой и наследуют ее контекст (даты, участники, ограничения, валюту).

Основные связи сущностей описываются следующим образом:
\begin{enumerate}
    \item Пользователь может участвовать в нескольких поездках, а одна поездка содержит нескольких участников.
    \item Идея принадлежит конкретной поездке и может быть преобразована в активность маршрута.
    \item Комментарии являются элементами обсуждения идеи и связаны с автором.
    \item Маршрут представлен набором дней, каждый день содержит упорядоченный список активностей.
    \item Расход относится к поездке и включает распределение долей между выбранными участниками.
    \item Погодные данные привязываются к выбранному городу и датам поездки.
    \item Предложение AI создается в контексте поездки и может быть сохранено как идея.
\end{enumerate}

Для серверного хранения применяется реляционная модель данных на основе PostgreSQL. В текущей реализации структура таблиц инициализируется схемой проекта и поддерживается в кодовой базе. На стороне клиента сохраняется локальное состояние, необходимое для восстановления пользовательского процесса при временной потере сети \sref{10}\sref{11}\sref{19}.

\subsection{Выбор методов и средств реализации}
Выбор методов и средств реализации выполнен по явным критериям: (1) поддержка мобильного сценария и офлайн-работы, (2) предсказуемость сопровождения, (3) совместимость со стеком Android/Backend, (4) стоимость доработок при расширении продукта.

\subsubsection{Серверная часть}
Серверная часть ориентирована на централизованную реализацию предметных правил и внешних интеграций. Выбран стек Kotlin + Ktor \sref{12}\sref{13} по следующим причинам:
\begin{enumerate}
    \item единый язык с клиентом снижает затраты на обучение и сопровождение команды;
    \item Ktor предоставляет REST и WebSocket в одном фреймворке, что покрывает сценарии API и обсуждений;
    \item стек допускает модульную структуру маршрутов и тестирование без сложной дополнительной инфраструктуры.
\end{enumerate}

В качестве альтернатив рассматривались Java/Spring и Node.js/Express; для данного проекта выбран Kotlin/Ktor как более совместимый со стеком Android и требованиями текущего проекта.

Архитектурно на сервере принят паттерн «маршрут -> предметный модуль -> репозиторий». Такой подход выбран для того, чтобы валидация входных данных, проверка ролей и операции с базой данных проходили через единые точки принятия решений.

\subsubsection{Хранилище данных}
Для транзакционного хранения предметных сущностей используется PostgreSQL \sref{10}\sref{11}. Выбор обусловлен:
\begin{enumerate}
    \item реляционной моделью с явными связями между поездками, участниками, идеями, маршрутом и расходами;
    \item транзакционными гарантиями ACID для операций, влияющих на совместное состояние группы;
    \item воспроизводимым развертыванием через инициализационную схему проекта.
\end{enumerate}

В качестве альтернатив рассматривались встраиваемые и документные хранилища; на текущем этапе они не обеспечивают такой же предсказуемости транзакционных операций для выбранной модели данных.

\subsubsection{Клиентская часть}
Мобильный клиент реализуется для платформы Android на Kotlin с Jetpack Compose, Hilt и Retrofit \sref{14}\sref{15}\sref{16}. Выбор обоснован:
\begin{enumerate}
    \item Compose --- декларативное управление состоянием сложных экранов и быстрые итерации UI;
    \item Hilt --- управляемая сборка зависимостей для модульных экранов;
    \item Retrofit/OkHttp --- типизированные клиентские контракты и стандартный стек сетевого взаимодействия.
\end{enumerate}

Альтернативный XML-based UI для текущего состава экранов не выбран из-за большей стоимости поддержки состояния и изменений интерфейса.

В клиентской архитектуре зафиксирована связка паттернов \texttt{MVVM + Repository + DI}:
\begin{enumerate}
    \item MVVM изолирует состояние экрана в \texttt{ViewModel} и делает поведение экрана воспроизводимым;
    \item Repository скрывает различия между сетевым источником, локальным кэшем и отложенной синхронизацией;
    \item DI (Hilt) снижает связанность модулей и упрощает модульное тестирование.
\end{enumerate}

\subsubsection{Интеграционные компоненты}
Для расширения пользовательского процесса в проекте используются внешние сервисы прогноза погоды и AI-генерации. В подсистеме офлайн-работы применяется механизм фоновой обработки задач синхронизации. Такой выбор позволяет сохранить работоспособность ключевых сценариев даже при частичной недоступности внешних источников \sref{17}\sref{18}\sref{19}.

Для интеграций используется адаптерный подход: вызовы внешних API инкапсулируются в отдельных компонентах, а прикладные модули работают с внутренними моделями. Это уменьшает объем изменений при замене провайдера и снижает риск каскадных правок в доменной логике.

\subsubsection{Обоснование выбранных паттернов}
Обоснование архитектурных паттернов в проекте сводится к проверяемым требованиям эксплуатации:
\begin{enumerate}
    \item сценарии выполняются в нестабильной сети, поэтому требуется раздельная обработка онлайн- и офлайн-путей (локальный кэш + очередь + фоновая синхронизация);
    \item в системе много экранов и форм, поэтому состояние интерфейса должно быть централизовано в \texttt{ViewModel}, а не распределено по компонентам UI;
    \item предметные ограничения (роли, принадлежность к поездке, валидность приглашения) должны проверяться на сервере в единых точках, чтобы избежать расхождений между сценариями;
    \item внешние сервисы могут быть частично недоступны или заменяться, поэтому интеграции изолируются адаптерным слоем;
    \item модульная декомпозиция по подсистемам уменьшает стоимость локальных изменений и снижает риск регрессий при доработках.
\end{enumerate}

\subsection{Нефункциональные решения}
Нефункциональные решения сформулированы с позиции эксплуатационной устойчивости и качества пользовательского опыта.

\begin{enumerate}
    \item \textbf{Согласованность данных.} Сервер обеспечивает единые правила валидации и хранения, а также разрешение коллизий при синхронизации, чтобы все участники поездки видели согласованное состояние после операций создания, изменения и удаления \sref{12}\sref{13}.
    \item \textbf{Надежность пользовательских сценариев.} Критические действия (идеи, маршрут, расходы) проектируются с учетом обработки ошибок и восстановления после сетевых сбоев \sref{7}\sref{19}.
    \item \textbf{Безопасность доступа.} В пользовательских сценариях доступ к действиям внутри поездки ограничен аутентификацией и участием пользователя в поездке; ролевые операции владельца и участника разграничены на уровне API-маршрутов модерации и управления доступом \sref{7}\sref{12}.
    \item \textbf{Интеграционная устойчивость.} При недоступности отдельных внешних сервисов базовые функции совместного планирования остаются доступными, а вспомогательные данные обновляются после восстановления интеграций \sref{17}\sref{18}.
    \item \textbf{Эксплуатационная применимость.} Архитектура допускает развертывание серверной части в облачной среде и публикацию мобильного клиента в стандартном канале распространения Android-приложений \sref{20}\sref{21}.
\end{enumerate}

Для проверки проектных решений, связанных с мобильной эксплуатацией, в текст включается отдельная иллюстрация офлайн-режима и восстановления согласованного состояния.

\subsection{Выводы по главе}

Сформированы проектные основания для реализации ключевых модулей: авторизации, управления поездкой и участниками, идей и обсуждений, маршрута, расходов, погодного и AI-контекста, уведомлений, офлайн-работы и синхронизации.
