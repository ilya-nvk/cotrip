## Аннотация
Настоящее техническое задание фиксирует ожидаемый пользовательский результат для мобильного приложения CoTrip.  
Документ описывает только пользовательски видимое поведение текущей версии проекта и не углубляется в архитектурные детали реализации.

Структура документа соответствует разделам ГОСТ-формата (1–8 + приложение), при этом содержание приведено к однозначным, проверяемым требованиям.

## Глоссарий
- **Приложение / CoTrip**: мобильное Android-приложение для совместного планирования поездок.
- **Пользователь**: авторизованный участник приложения.
- **Поездка**: общий объект планирования с датами, участниками, идеями, маршрутом и расходами.
- **Владелец поездки**: пользователь, создавший поездку и управляющий доступом/модерацией в ней.
- **Участник поездки**: пользователь, присоединившийся к поездке.
- **Идея**: предложение места/активности до включения в маршрут.
- **Активность**: элемент маршрута, назначенный на конкретный день поездки.
- **Расход**: запись о планируемой или оплаченной сумме в рамках поездки.
- **Предложение AI**: автоматически сгенерированная рекомендация активности, которую можно сохранить в идеи.

Для единообразия в документе используются только термины из этого раздела.

## 1 ВВЕДЕНИЕ

### 1.1 Наименование программы
- Наименование на русском: **«Андроид-приложение для совместного планирования поездок»**.
- Наименование на английском: **«Android Application for Collaborative Trip Planning»**.
- Краткое имя продукта: **CoTrip**.

### 1.2 Краткая характеристика области применения программы
Приложение предназначено для пользователей, которые планируют поездки в группе: согласуют план по дням, обсуждают идеи, распределяют расходы, отслеживают погоду и используют AI-подсказки для маршрута.

## 3 НАЗНАЧЕНИЕ РАЗРАБОТКИ

### 3.1 Функциональное назначение
Приложение должно обеспечивать единый пользовательский сценарий совместного планирования поездки:
- вход и управление профилем;
- создание и ведение поездок;
- приглашение и управление участниками;
- работу с идеями и обсуждениями;
- формирование маршрута по дням;
- учет расходов и отображение балансов;
- просмотр прогноза погоды;
- генерацию и сохранение AI-предложений.

### 3.2 Эксплуатационное назначение
Приложение предназначено для смартфонов на Android и используется конечными пользователями без специальной технической подготовки.

## 4 ТРЕБОВАНИЯ К ПРОГРАММЕ

### 4.1 Требования к функциональным характеристикам

#### 4.1.1 Шаблон формулирования требований
Каждый функциональный модуль в данном ТЗ описывается по единому шаблону:
- **Предусловия**;
- **Действия пользователя**;
- **Ожидаемый результат**;
- **Ограничения/валидации**;
- **Критерий приемки**.

#### 4.1.2 Авторизация и профиль
**Предусловия**  
Пользователь установил приложение, устройство подключено к интернету.

**Действия пользователя**  
Пользователь выполняет вход через Google, затем в настройках меняет имя/фото, выходит из аккаунта или удаляет профиль.

**Ожидаемый результат**
- После успешного входа открывается экран списка поездок.
- Имя и фото профиля сохраняются и отображаются в настройках.
- При выходе доступ к данным закрывается до повторного входа.
- При удалении профиля доступ к аккаунту прекращается, пользователь возвращается на экран входа.

**Ограничения/валидации**
- Имя профиля не должно быть пустым.
- При отсутствии сети вход не выполняется, пользователю показывается сообщение об ошибке.

**Критерий приемки**  
Пользователь может завершить полный цикл: вход -> изменение профиля -> выход -> повторный вход.

#### 4.1.3 Поездки
**Предусловия**  
Пользователь авторизован.

**Действия пользователя**  
Пользователь создает поездку, редактирует ее параметры, просматривает карточку поездки, удаляет поездку.

**Ожидаемый результат**
- Новая поездка создается с названием, датами, валютой, описанием и обложкой (при наличии).
- Поездка отображается в списке, а пользователь может открыть экран ее деталей.
- При редактировании данные поездки обновляются и сохраняются.
- При удалении поездка удаляется из пользовательского списка.

**Ограничения/валидации**
- Название поездки обязательно.
- Дата начала не может быть в прошлом.
- Дата окончания не может быть раньше даты начала.
- Диапазон дат должен быть допустимым для создания/редактирования.

**Критерий приемки**  
После создания поездки и обновления данных изменения сохраняются и видны после повторного открытия экрана.

#### 4.1.4 Приглашения и присоединение
**Предусловия**  
Пользователь является владельцем поездки.

**Действия пользователя**  
Владелец создает ссылку-приглашение, копирует/делится ей; другой пользователь присоединяется по ссылке или валидному приглашению.

**Ожидаемый результат**
- Ссылка-приглашение генерируется и может быть передана вне приложения.
- Получатель приглашения может присоединиться к поездке.
- После присоединения поездка появляется у нового участника, а в списке участников отображается новый человек.

**Ограничения/валидации**
- Присоединение по невалидной/просроченной ссылке не выполняется.
- Повторное присоединение в уже добавленную поездку не дублирует участника.

**Критерий приемки**  
Ссылка, созданная владельцем, позволяет второму пользователю войти в ту же поездку и открыть ее детали.

#### 4.1.5 Идеи и обсуждения
**Предусловия**  
Пользователь является участником поездки.

**Действия пользователя**  
Пользователь добавляет/редактирует/удаляет идею, открывает обсуждение идеи, публикует комментарии; владелец одобряет или отклоняет идею; участник переносит идею в маршрут.

**Ожидаемый результат**
- Идея появляется в списке идей поездки.
- Изменения идеи сохраняются и отображаются после обновления экрана.
- Комментарии отображаются в обсуждении и обновляются у участников в живом режиме.
- Для идеи отображается актуальный статус (ожидает/одобрена/отклонена).
- Идея может быть добавлена в выбранный день маршрута.

**Ограничения/валидации**
- Заголовок идеи обязателен.
- Комментарий не может быть пустым.
- Удаление комментария доступно только в допустимом пользовательском сценарии (авторский комментарий).

**Критерий приемки**  
Комментарий, отправленный одним участником, появляется в обсуждении у другого участника без ручной перезагрузки экрана.

#### 4.1.6 Маршрут (дни и активности)
**Предусловия**  
Поездка создана.

**Действия пользователя**  
Пользователь открывает маршрут, выбирает город для дня, создает/редактирует/удаляет активность, меняет порядок и переносит активность между днями.

**Ожидаемый результат**
- Маршрут отображается по дням поездки.
- Для дня можно выбрать город из предложенных вариантов.
- Активность можно добавить, изменить, удалить, переместить и переупорядочить.
- При изменении дат поездки обрабатываются дни вне диапазона (пользователь выбирает продление дат или удаление таких дней).

**Ограничения/валидации**
- Активность не может быть создана без названия.
- Действия с прошедшей поездкой ограничиваются режимом просмотра.

**Критерий приемки**  
После перемещения и переупорядочивания активностей порядок сохраняется после повторного открытия маршрута.

#### 4.1.7 Расходы и балансы
**Предусловия**  
В поездке есть участники.

**Действия пользователя**  
Пользователь создает расход (planned/paid), выбирает участников, тип разделения (поровну/кастомно), указывает плательщика, обновляет статус и отметки оплаты.

**Ожидаемый результат**
- Расход сохраняется в поездке и отображается в списке расходов.
- На экране расходов видны суммарные показатели и персональный баланс пользователя.
- Для расхода в деталях отображается распределение долей и статус оплаты по участникам.

**Ограничения/валидации**
- Заголовок и сумма расхода обязательны.
- Для расхода должен быть выбран минимум один участник.
- Нельзя создать расход в валюте, отличной от валюты поездки.

**Критерий приемки**  
После добавления оплаченного расхода итоговые суммы и баланс на экране расходов пересчитываются корректно.

#### 4.1.8 Погода
**Предусловия**  
В маршруте поездки выбран хотя бы один город.

**Действия пользователя**  
Пользователь открывает прогноз, переключает город (если доступно несколько), запускает обновление прогноза.

**Ожидаемый результат**
- Отображается прогноз по выбранному городу поездки.
- Показывается покрытие данных по датам (если часть дат недоступна, это явно отражается в интерфейсе).
- Обновление прогноза доступно вручную, а также может запускаться автоматически при открытии и возврате на экран прогноза.

**Ограничения/валидации**
- Прогноз не должен отображаться для невыбранного города.
- При отсутствии доступных данных пользователь получает информативное сообщение.

**Критерий приемки**  
После ручного или автоматического обновления пользователь видит актуальные погодные данные или явное сообщение о недоступности части дат.

#### 4.1.9 AI-подсказки
**Предусловия**  
Пользователь находится в поездке и открыл раздел генерации подсказок.

**Действия пользователя**  
Пользователь выбирает город и фильтры, запускает генерацию, сохраняет понравившееся предложение в идеи.

**Ожидаемый результат**
- Пользователь получает список AI-предложений.
- Каждое предложение может быть сохранено в идеи поездки.
- Сохраненное предложение помечается как сохраненное.

**Ограничения/валидации**
- Генерация доступна при выбранном городе.
- При временной недоступности генерации пользователь получает сообщение об ошибке.

**Критерий приемки**  
После сохранения AI-предложения оно появляется в списке идей соответствующей поездки.

#### 4.1.10 Настройки и уведомления
**Предусловия**  
Пользователь авторизован.

**Действия пользователя**  
Пользователь открывает настройки, переключает категории уведомлений, возвращается в приложение после системного уведомления.

**Ожидаемый результат**
- Переключатели уведомлений сохраняют выбранное состояние.
- При включенных категориях уведомлений, выданном системном разрешении и доступном интернете системные push-уведомления по ключевым событиям поездки доставляются и ведут пользователя в релевантный сценарий приложения.

**Ограничения/валидации**
- Категории уведомлений должны быть доступны для управления из настроек.

**Критерий приемки**  
После изменения переключателей и повторного открытия настроек состояния остаются сохраненными.

#### 4.1.11 Офлайн-поведение и синхронизация
**Предусловия**  
Пользователь уже работал с поездкой и часть данных загружена.

**Действия пользователя**  
Пользователь открывает приложение при нестабильной/отсутствующей сети и продолжает работу в доступных сценариях.

**Ожидаемый результат**
- Ранее загруженные данные продолжают отображаться.
- Операции создания, изменения и удаления в поддерживаемых сущностях могут фиксироваться локально в офлайн-очередь без аварийного завершения приложения.
- После восстановления сети офлайн-очередь отправляется на сервер, а итоговое состояние данных согласуется с применением серверной стратегии разрешения коллизий.

**Ограничения/валидации**
- Без сети не гарантируется немедленное подтверждение операций от серверного контура.

**Критерий приемки**  
После восстановления сети пользователь видит актуализацию данных, включая результаты офлайн-операций создания/изменения/удаления, без переустановки приложения.

#### 4.1.12 Явные границы текущей версии
В текущую версию **не входят** требования:
- просмотр маршрута на карте;
- универсальный глобальный поиск/фильтры по тегам/категориям для всех сущностей;
- сценарии, доступные только на уровне API и не представленные в пользовательских экранах.

### 4.2 Требования к временным характеристикам
- Во всех пользовательских операциях ожидания должны отображаться индикаторы загрузки.
- Приложение не должно «зависать» без обратной связи пользователю при обработке запроса.

### 4.3 Требования к интерфейсу
- Интерфейс должен соответствовать мобильному формату Android и быть пригодным для повседневного использования без обучения.
- Основные действия должны выполняться через явные элементы управления (кнопки, поля ввода, селекторы дат/списков).
- Навигация между ключевыми разделами должна быть последовательной и предсказуемой.

### 4.4 Требования к надежности
- Приложение должно корректно обрабатывать ошибки сети и серверные ошибки с понятными сообщениями.
- Некорректный ввод пользователя не должен приводить к аварийному завершению.
- После перезапуска приложения пользователь должен иметь возможность продолжить работу со своими данными.

### 4.5 Условия эксплуатации
- Эксплуатация выполняется на персональных Android-смартфонах в условиях, заявленных производителем устройства.
- Для полной функциональности требуется доступ к интернету.

### 4.6 Требования к составу и параметрам технических средств
- Мобильное устройство на Android `8.0+` (API 26 и выше).
- Наличие доступа к сети Интернет.

### 4.7 Требования к информационной и программной совместимости
- Приложение должно корректно работать в целевой версии Android и поддерживать обновление пользовательских данных между сессиями.
- Обработка пользовательских данных должна выполняться в рамках применимого законодательства о персональных данных.

### 4.8 Требования к маркировке и упаковке
- Приложение распространяется через стандартные каналы дистрибуции Android-приложений.

### 4.9 Требования к транспортированию и хранению

## 8 ПОРЯДОК КОНТРОЛЯ И ПРИЕМКИ

### 8.1 Виды испытаний
- Ручное функциональное тестирование ключевых пользовательских сценариев.
- Проверка интерфейсной целостности и навигации.
- Проверка устойчивости при ошибках сети и повторных запусках.

### 8.2 Общие требования к приемке работы
Работа принимается при выполнении следующих условий:
- реализованы и подтверждены пользовательские сценарии из раздела 4.1;
- отсутствуют противоречия между требованиями и фактическим поведением приложения;
- документация оформлена и согласована.

### 8.3 Приемочные сценарии (Given/When/Then)

#### Сценарий 1. Авторизация
**Given** пользователь не авторизован  
**When** пользователь выполняет вход через Google  
**Then** открывается список поездок, сессия активна.

#### Сценарий 2. Профиль
**Given** пользователь в разделе настроек  
**When** он меняет имя и сохраняет  
**Then** новое имя отображается после повторного открытия настроек.

#### Сценарий 3. Поездка
**Given** пользователь на экране списка поездок  
**When** он создает поездку с валидными датами  
**Then** поездка появляется в списке и доступна для открытия.

#### Сценарий 4. Приглашение
**Given** владелец поездки создал ссылку-приглашение  
**When** другой пользователь открывает ссылку и подтверждает вход  
**Then** он становится участником поездки и видит ее детали.

#### Сценарий 5. Идеи и обсуждения
**Given** два участника находятся в одной поездке  
**When** первый участник отправляет комментарий к идее  
**Then** второй участник видит комментарий в обсуждении без ручного обновления.

#### Сценарий 6. Маршрут
**Given** в поездке есть дни маршрута  
**When** пользователь добавляет активность и меняет ее порядок  
**Then** новый порядок сохраняется после повторного открытия маршрута.

#### Сценарий 7. Out-of-range дни
**Given** при редактировании дат появились дни вне диапазона  
**When** пользователь выбирает «продлить окончание поездки»  
**Then** маршрут остается целостным и дни больше не считаются вне диапазона.

#### Сценарий 8. Расходы
**Given** в поездке есть минимум два участника  
**When** пользователь создает оплаченный расход с распределением долей  
**Then** обновляются список расходов, итоговые суммы и баланс.

#### Сценарий 9. Погода
**Given** в маршруте выбран город  
**When** пользователь открывает прогноз (или возвращается на экран) и при необходимости запускает обновление вручную  
**Then** отображаются доступные погодные данные и сообщение о покрытии дат.

#### Сценарий 10. AI-подсказки
**Given** пользователь открыл генерацию подсказок  
**When** он запускает генерацию и сохраняет одно предложение  
**Then** сохраненное предложение появляется в идеях поездки.

#### Сценарий 11. Настройки уведомлений
**Given** пользователь в настройках уведомлений  
**When** он изменяет переключатели категорий  
**Then** выбранные состояния сохраняются после повторного открытия экрана.

#### Сценарий 12. Офлайн и восстановление сети
**Given** пользователь временно потерял сеть  
**When** пользователь создает/изменяет/удаляет данные в офлайн-режиме, затем сеть восстанавливается и экран обновляется  
**Then** офлайн-очередь отправляется, данные поездки актуализируются, а конфликтные изменения разрешаются сервером без ручного вмешательства пользователя.
